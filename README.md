# 꽥꽥이 Frontend

대화하는 오리 친구 꽥꽥이의 React + TypeScript + Vite 기반 프론트엔드입니다. 기술 선택과 작업 규칙은 [AGENTS.md](./AGENTS.md)를 따릅니다.

## 실행

Node.js 24 LTS와 npm을 사용합니다. `.nvmrc`에 Node 버전을 지정했습니다.

```sh
nvm use
npm ci
cp .env.example .env.local
npm run dev
```

개발 서버는 기본적으로 `http://localhost:5173`에서 실행됩니다. `.env.local`의 `VITE_API_BASE_URL`을 백엔드 주소에 맞게 변경합니다. 백엔드에서도 프론트엔드 Origin을 CORS 허용 목록에 등록해야 합니다.

`/`는 로그인 상태이면 `/chats`, 비로그인 상태이면 `/login`으로 이동합니다. 로그인 후 `/chats`는 꽥꽥이 환영 화면과 `새 대화 시작` 버튼, 기존 대화 목록을 표시합니다. 버튼으로 세션을 생성하면 `/chats/:chatId`로 이동하고, 대화 목록과 선택한 세션의 기록을 확인할 수 있습니다. `/login`과 `/signup`에서 로그인·회원가입 화면을 확인할 수 있습니다. 그 외 주소는 404 안내와 처음 화면으로 돌아가는 링크를 제공합니다. 회원·채팅 요청은 아래 MSW 실행 방식으로 백엔드 없이 확인할 수 있습니다. 일반 실행에서는 실제 백엔드에 요청합니다. 회원가입과 채팅 생성·조회·질문 전송, 관리자 조회를 연결했습니다. 로그인은 실제 API로 토큰을 받아 채팅 요청에 사용합니다. 대화 삭제는 백엔드에 아직 없으므로 MSW 미리보기에서만 사용할 수 있습니다.

## 환경 변수

| 변수                      | 설명                                        | 기본값                  |
| ------------------------- | ------------------------------------------- | ----------------------- |
| `VITE_API_BASE_URL`       | 백엔드 Origin. `/api/v1`은 요청 경로에 포함 | `http://localhost:8000` |
| `VITE_ENABLE_MSW`         | 로컬·Preview API 모킹 활성화 여부           | `false`                 |
| `VITE_CHAT_MOCK_SCENARIO` | MSW 채팅 화면 검증 시나리오                 | 기본 예시               |

`VITE_`로 시작하는 값은 브라우저에 공개됩니다. 비밀 키나 서버 인증 정보를 넣지 않습니다.

Railway 개발 백엔드에 연결할 때는 `.env.local`과 Vercel의 해당 배포 환경에 다음 값을 설정합니다. 환경 변수를 변경하면 로컬 개발 서버를 재시작하거나 Vercel에서 다시 배포합니다.

```dotenv
VITE_API_BASE_URL=https://be-b7-1-development.up.railway.app
VITE_ENABLE_MSW=false
```

백엔드의 `CORS_ORIGINS`에는 실제 프론트 Origin이 허용되어 있어야 합니다. 로컬 개발 주소는 `http://localhost:5173`과 `http://127.0.0.1:5173`, 배포 프론트 주소는 `https://www.quackquack-e.duckdns.org`입니다. API가 직접 호출될 때 정상 응답하더라도 CORS 허용 목록에서 빠진 브라우저에서는 요청할 수 없습니다.

## API 요청

`src/lib/api.ts`의 `apiRequest`를 사용합니다. JSON 응답을 반환하며, HTTP 오류는 상태 코드·메시지·오류 코드(`code`)·요청 ID(`requestId`)를 가진 `ApiError`로 전달합니다. 네트워크 오류는 fetch의 오류를 그대로 전달합니다. 채팅 요청에는 로그인 토큰을 `Authorization: Bearer` 헤더로 전달합니다. 로그인·회원가입 요청에는 토큰을 붙이지 않습니다. 보호 API의 `401`은 인증 상태를 정리하며, 로그인 실패의 `401`은 입력 오류로 표시합니다. 인증 상태가 바뀐 뒤 도착한 이전 요청의 응답은 화면에 반영하지 않습니다.

```ts
import { apiRequest } from './lib/api';

const response = await apiRequest<{ message: string }>('/api/example');

// JSON 본문은 명시적으로 직렬화하고 Content-Type을 지정합니다.
await apiRequest('/api/example', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ message: 'hello' }),
});
```

위 경로는 세팅 설명용 예제이며 실제 백엔드 계약이 아닙니다. 타입 매개변수는 응답 타입 선언으로, 런타임 검증을 수행하지 않습니다. 실제 계약에 맞춰 기능별 요청 함수를 추가합니다.

## 백엔드 API 연결 상태

현재 백엔드 코드의 경로 접두어는 `/api/v1`입니다. `VITE_API_BASE_URL`에는 이 접두어를 중복해서 넣지 않습니다. 일반 개발은 `npm run dev`, 백엔드 없이 확인하는 미리보기는 `npm run dev:mock`을 사용합니다.

| 기능                       | 서버 경로                                                                          | 현재 상태                                 |
| -------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------- |
| 회원가입                   | `POST /api/v1/auth/signup`                                                         | 실제 DB 저장                              |
| 로그인                     | `POST /api/v1/auth/login`                                                          | Bearer 토큰 발급, 기본 30분 만료          |
| 채팅 생성·목록             | `POST /api/v1/chats`, `GET /api/v1/chats`                                          | 실제 DB 연결, Bearer 토큰의 로그인 사용자 |
| 채팅 상세·질문 전송        | `GET /api/v1/chats/:chatId`, `POST /api/v1/chats/:chatId/messages`                 | 실제 DB·AI 연결                           |
| 관리자 회원·세션·대화 조회 | `GET /api/v1/admin/users`, `/users/:id`, `/sessions`, `/sessions/:chatId`, `/logs` | 서버 내부 임시 데이터                     |
| 관리자 시스템 로그         | `GET /api/v1/admin/system-logs`                                                    | 서버 JSONL 파일 조회                      |
| 대화 삭제                  | `DELETE /api/v1/chats/:chatId`                                                     | 본인 대화 논리 삭제, 성공 시 204          |

채팅 생성·조회·질문 전송은 로그인한 사용자 기준으로 처리합니다. 비로그인 상태에서 `/chats`, 대화 상세, 관리자 화면에 접근하면 로그인 화면으로 이동하며 채팅 API를 호출하지 않습니다. 로그인 상태에서 `/login`·`/signup`에 접근하면 `/chats`로 이동합니다. AI 질문 전송은 백엔드의 유효한 `OPENAI_API_KEY`·모델 설정이 있어야 성공하며, 설정 누락·시간 초과·AI 오류는 서버 메시지로 표시합니다.

회원가입으로 생성된 실제 회원·대화는 아직 관리자 임시 저장소에 반영되지 않습니다. 프론트에서 임시 데이터를 실제 데이터처럼 합치거나 로그인 상태를 만들어내지 않습니다.

## MSW

```sh
npm run dev:mock
```

`.env.mock`으로 모킹을 활성화하며, worker가 준비된 뒤 앱을 표시합니다. 모드별 설정인 `.env.mock`은 `.env.local`보다 우선 적용됩니다. 개인 모킹 설정이 필요하면 Git에서 제외되는 `.env.mock.local`에 지정합니다.

- `src/mocks/handlers.ts`: 실제 API 응답 형식에 맞춘 모킹과 성공·지연·실패 시나리오 정의. 로그인 성공 응답은 실제 API와 같은 토큰 형식이고 채팅 handler에서도 토큰을 확인합니다.
- `src/mocks/browser.ts`: 브라우저용 worker. 모킹 중 처리하지 않은 API 요청은 오류로 차단하고, 화면 리소스 요청은 통과시킵니다.
- `src/mocks/server.ts`: 테스트용 모킹 서버.
- `public/mockServiceWorker.js`: MSW가 생성하는 파일. 직접 수정하지 않습니다.

MSW 패키지 업데이트 후에는 `npx msw init public --save`로 worker를 갱신합니다. worker는 `VITE_ENABLE_MSW=true`가 명시된 빌드에서만 시작합니다. 기본 배포용 빌드에서는 비활성화됩니다.

### 회원가입과 로그인

회원가입은 `POST /api/v1/auth/signup`에 `{ name, username, password }`를 전송합니다. 비밀번호 확인 값은 프론트에서 비교하며 서버에 보내지 않습니다.

- 아이디: 영문·숫자·밑줄 4~20자. 공백·하이픈은 허용하지 않으며, 서버는 소문자로 저장하고 대소문자를 구분하지 않고 중복 검사합니다.
- 비밀번호: 8~128자. 앞뒤 공백을 포함한 원문을 그대로 전송합니다.
- 이름: 앞뒤 공백을 제거한 후 1~50자.
- 성공: `201`과 `{ id, username, name, created_at }` 응답 후 로그인 화면으로 이동하고 가입 완료를 표시합니다.
- 아이디 중복: 회원가입 응답의 `409 USERNAME_TAKEN`을 아이디 입력란에 표시합니다. 중복 검사는 회원가입 요청으로 처리합니다.
- 실패: 입력을 유지하며 다시 제출할 수 있습니다. 요청 중 입력 변경과 중복 제출을 막습니다.

로그인은 `POST /api/v1/auth/login`에 `{ username, password }`를 보내고 `{ access_token, token_type, expires_in }`을 받습니다. 아이디는 회원가입과 같은 입력 규칙을 적용하며 비밀번호 공백을 보존합니다. 성공하면 `/chats`로 이동합니다.

토큰과 만료 시각은 `sessionStorage`의 `quackquack.auth`에 저장하고 Context로 인증 상태를 공유합니다. 새로고침하면 저장된 유효한 세션을 복원하고, 손상·만료된 세션은 제거합니다. 만료 시각 도달·백그라운드 화면 복귀·보호 API의 `401` 응답 시 세션을 정리하고 로그인 화면으로 이동합니다. 갱신 API가 없으므로 자동 갱신 요청을 보내지 않습니다.

로그아웃 버튼은 프론트 토큰과 인증 상태를 제거하고 대화 화면의 목록·기록·입력을 정리합니다. 서버 로그아웃 API는 없으며 서버에서 발급된 토큰을 폐기하는 동작은 수행하지 않습니다.

내 정보 API가 없어 사용자 이름과 권한은 저장하지 않습니다. 현재 로그인 후에는 모두 `/chats`로 이동합니다. 관리자 권한별 이동·메뉴 표시·접근 제어는 내 정보 API 준비 후 진행합니다. 현재 관리자는 로그인 여부만 확인하며 실제 관리자 권한 검사를 대신하지 않습니다.

| 입력 아이디                              | MSW 시나리오                 |
| ---------------------------------------- | ---------------------------- |
| `new_friend` 등 아래 예약 값 외의 아이디 | 가입 성공                    |
| `duck`, `taken` 및 대소문자 변형         | 가입 시 중복 오류            |
| `signup_error`                           | 가입 서버 오류               |
| `friend`                                 | 로그인 성공 및 토큰 발급     |
| `wrong`                                  | 401 INVALID_CREDENTIALS      |
| `error`                                  | 503 AUTH_CONFIGURATION_ERROR |

MSW도 가입한 아이디를 소문자로 기억하고 같은 아이디의 재가입을 거절합니다. 새로고침하면 이 미리보기 데이터는 초기화됩니다.

배포 빌드에서도 모킹이 동작하는지 로컬에서 확인하려면 다음과 같이 실행합니다.

```sh
npm run build:mock
npm run preview
```

### 채팅 화면 미리보기

채팅 생성·목록·상세·질문 전송 요청은 `reference/채팅-api-명세서.md`의 `/api/v1/chats` 계약을 사용합니다. 응답 데이터와 세션 상태는 기존 `src/mocks/handlers.ts`에서 관리하며, 화면은 공통 요청 함수를 사용합니다.

- `/chats`: 대화 화면과 같은 레이아웃에서 왼쪽 목록·새 대화 시작 버튼, 오른쪽 환영 화면 표시. 대화 선택 시 오른쪽 영역이 대화창으로 전환됩니다.
- `/chats/:chatId`: 왼쪽 목록에서 세션 전환·새 대화 생성, 오른쪽에서 기록 확인. 데스크톱에서는 최대 너비 제한 없이 남은 화면 높이를 활용하고 목록과 대화 기록이 각각 내부에서 스크롤됩니다. 모바일에서는 목록이 위에 표시됩니다.
- 생성 요청은 본문 없이 전송하며, 응답의 세션을 목록에 반영하고 해당 주소로 이동합니다.
- 각 세션의 삭제 버튼에서 확인·취소할 수 있습니다. 삭제 중에는 확인창을 닫거나 중복 제출할 수 없고, 실패하면 목록·현재 대화·확인창을 유지해 재시도합니다. 현재 대화 삭제 시 홈으로 이동하고 다른 대화 삭제 시 현재 화면을 유지합니다.
- 대화 삭제는 Bearer 토큰을 포함해 `DELETE /api/v1/chats/:chatId`로 요청합니다. 성공 시 본문 없는 204 응답을 받아 목록에서 제거합니다. 백엔드는 본인 대화에 삭제 시각을 기록하고 목록·상세 조회에서 제외합니다. 이미 없는 세션(404)도 목록에서 제거하며, 인증 오류(401)는 로그인 화면으로 이동합니다.
- 기본 예시는 완료된 대화, 긴 내용·실패·처리 중 기록을 포함한 대화, 빈 대화입니다. 시각은 KST로 표시합니다.
- 생성된 세션은 MSW 메모리에만 유지됩니다. 새로고침하면 초기 예시로 돌아가며, 새로 만든 세션의 주소는 더 이상 조회되지 않습니다. 기본 예시 주소는 직접 접근·새로고침으로 다시 열 수 있습니다.
- 질문은 `POST /api/v1/chats/:chatId/messages`로 전송하고, 완료된 질문·답변 한 건을 받아 기록에 반영합니다. 전송 중에는 질문과 로딩을 표시하며, 2초 이상 기다리면 대기 안내를 표시합니다.
- Enter는 전송, Shift+Enter는 줄바꿈입니다. 한글 조합 중 Enter는 전송하지 않습니다. 공백만 있는 입력은 전송할 수 없고, 전송 중 중복 제출을 막습니다. 서버와 같이 앞뒤 공백을 제거하고 최소 1자를 요구합니다. 현재 서버에 최대 길이 제한은 없습니다.
- 실패 시 입력과 기존 기록을 유지하고, 서버 오류·처리 중 오류에서는 상세를 다시 조회해 서버가 저장한 기록을 반영합니다. 입력을 그대로 다시 보낼 수 있습니다.
- 세션 이동 시 이전 요청의 화면 반영을 중단합니다. 서버 역할의 MSW는 진행 중 처리를 마치며, 해당 세션을 다시 조회하면 저장된 기록을 확인할 수 있습니다. 전송하지 않은 입력은 세션 이동 시 초기화됩니다.
- 실제 AI 호출 없이 MSW가 예시 답변을 반환합니다. 긴 질문·줄바꿈이 있는 질문에는 긴 답변을 반환해 말풍선과 스크롤을 확인할 수 있습니다. 처리 중 예시 기록이 있는 세션에 전송하면 `409 CHAT_BUSY`로 응답합니다.

채팅 예시는 로그인 후 확인합니다. MSW에서도 `friend` 등으로 로그인하면 토큰을 발급하며, 누락·알 수 없는 토큰·만료 토큰은 `401 UNAUTHORIZED`로 처리합니다.

빈 목록과 오류 화면은 `.env.mock.local`의 `VITE_CHAT_MOCK_SCENARIO`로 선택합니다. 값 변경 후 개발 서버를 재시작하고 브라우저를 새로고침합니다. 배포 빌드는 다시 빌드합니다.

| 값             | 검증 대상                                           |
| -------------- | --------------------------------------------------- |
| 미설정         | 기본 예시·세션 생성·조회                            |
| `empty`        | 빈 목록에서 새 대화 시작                            |
| `list-error`   | 목록 조회 실패·재시도                               |
| `create-error` | 생성 실패 시 기존 선택·기록 유지                    |
| `detail-error` | 상세 조회 실패·재시도                               |
| `send-error`   | 세션별 첫 전송 실패(502)·입력 유지·재전송 성공      |
| `delete-error` | 세션별 첫 삭제 실패(500)·기존 선택 유지·재시도 성공 |
| `timeout`      | 세션별 첫 전송 시간 초과(504)·재전송 성공           |
| `slow`         | 질문 응답 3.5초 지연·대기 안내·중복 제출·세션 전환  |

목록·생성·상세 오류 시나리오는 설정이 유지되는 동안 같은 실패 응답을 반환합니다. `send-error`와 `timeout`은 세션별 첫 전송만 실패하고 다음 전송은 성공합니다. `delete-error`는 세션별 첫 삭제만 실패하고 재시도하면 성공합니다. 실패 기록도 MSW에 저장되며, 새로고침하면 세션 데이터와 실패 횟수가 초기화됩니다. 테스트에서도 데이터를 초기화하고 오류 후 성공·네트워크 오류·빠른 전환을 검증합니다.

## 테스트와 로컬 검사

`src/test/setup.ts`에서 React Testing Library와 MSW를 초기화합니다. 각 테스트 후 화면과 임시 handler를 정리하며, 테스트 중 처리하지 않은 네트워크 요청은 오류로 처리합니다.

현재 테스트는 기본 라우팅·404 복귀·공통 API 요청과 회원 화면의 입력·확인·가입 흐름, 채팅 생성·선택·삭제 확인·취소·실패 후 재시도·삭제 후 선택과 빈 목록·질문 전송·한글 입력·긴 내용·실패 후 재시도·지연 안내·늦은 응답 처리를 검증합니다.

`npm run check`로 형식 검사, 코드 검사, 테스트, 빌드를 로컬에서 실행합니다.

## Vercel

1. Vercel에서 이 GitHub 저장소를 연결합니다.
2. Framework는 Vite, Build Command는 `npm run build`, Output Directory는 `dist`로 설정합니다. `vercel.json`에도 지정되어 있습니다.
3. `VITE_API_BASE_URL`에 실제 HTTPS 백엔드 주소를 설정합니다.
4. 백엔드 CORS 설정에 배포된 프론트엔드 Origin을 추가합니다.

퍼블리싱 리뷰용 Preview에서는 `VITE_ENABLE_MSW=true`를 **Preview 환경에만** 설정하고 새로 배포합니다. Build Command는 기존 `npm run build`를 유지해도 됩니다. Production은 `false` 또는 미설정으로 유지합니다. 환경 변수 변경은 이미 만들어진 배포에 적용되지 않습니다. 활성화된 모킹은 API 기본 주소가 로컬 기본값이어도 회원·채팅 요청을 모두 가로채며, 등록되지 않은 API 요청도 백엔드로 전달하지 않습니다. 실제 Vercel 환경 변수 설정과 배포 확인은 별도로 진행합니다.

`vercel.json`의 rewrite는 React Router 경로를 직접 열거나 새로고침할 때도 앱을 표시하도록 설정합니다.

## 관리자 화면

로그인 후 사용자 화면의 상단 `관리자` 링크 또는 `/admin`으로 접근합니다. 프론트는 로그인 여부를 확인하지만 백엔드의 관리자 인증은 아직 임시 통과 상태입니다. 내 정보 API의 권한을 이용한 메뉴 표시·화면 이동·접근 제한과 서버 관리자 권한 검사는 후속 작업입니다. 사용자 화면은 `quack`, 관리자 레이아웃 전체는 daisyUI 기본 `light` 테마를 사용합니다.

| 경로                      | 확인할 내용                                   |
| ------------------------- | --------------------------------------------- |
| `/admin/users`            | 회원 목록·페이지·페이지당 표시 개수           |
| `/admin/users/:userId`    | 회원 정보·최근 로그인·회원별 대화 세션        |
| `/admin/sessions/:chatId` | 세션별 질문·답변·처리 중·실패 기록            |
| `/admin/logs`             | 회원·기간별 대화 기록·세션 상세 이동          |
| `/admin/system-logs`      | 레벨·이벤트·기간별 시스템 로그·회원 상세 이동 |

조회 요청은 `/api/v1/admin/users`, `/users/:userId`, `/sessions`, `/sessions/:chatId`, `/logs`, `/system-logs`를 사용합니다. 위 첫 경로를 제외한 나머지 경로에도 `/api/v1/admin` 접두어가 적용됩니다. 백엔드의 관리자 문서·응답 스키마에 맞춰 `items`, `total`, `page`, `size`를 사용하며, 세션 목록 요청에는 `user_id`가 필수입니다.

페이지와 조회 조건은 URL에 저장됩니다. 조건·표시 개수 변경 시 첫 페이지로 이동하고, 새로고침·뒤로 가기에서 선택한 조건을 복원합니다. 기간은 KST로 입력하고 UTC ISO 8601의 `start`, `end`로 요청합니다. 시작·종료 시각은 양 끝을 포함하며, 기간을 거꾸로 입력하면 요청 전 오류를 표시합니다.

기본 MSW 예시는 회원 24명과 시스템 로그 31건을 제공합니다. 회원 1은 기본 완료·빈 대화와 새로 생성한 대화, 회원 2는 긴 내용·실패·처리 중 예시 대화를 조회합니다. 다른 회원은 빈 세션 상태를 확인할 수 있습니다. 회원·세션·대화는 기존 채팅 MSW 데이터를 사용하므로 사용자 화면의 생성·전송·삭제 결과도 조회에 반영됩니다. 예시 회원 관계는 실제 인증·소유권 확인을 대체하지 않습니다. 시스템 로그는 동일한 내용의 로그와 식별자가 없는 로그도 각각 표시합니다.

`.env.mock.local`에서 `VITE_ADMIN_MOCK_SCENARIO`를 지정한 뒤 개발 서버 재시작·브라우저 새로고침으로 상태를 확인할 수 있습니다. 빌드에서 바꾸려면 다시 빌드합니다.

| 값                                | 확인할 상태                |
| --------------------------------- | -------------------------- |
| 미설정                            | 기본 조회·필터·페이지 이동 |
| `empty`                           | 목록별 빈 결과             |
| `error`                           | 관리자 조회 전체 오류      |
| `users-error`, `user-error`       | 회원 목록·상세 오류        |
| `sessions-error`, `session-error` | 세션 목록·상세 오류        |
| `logs-error`, `system-error`      | 대화 기록·시스템 로그 오류 |
| `slow`                            | 관리자 조회 1.5초 지연     |

실패 상태에서는 재시도할 수 있고, 없는 회원·세션은 404 안내를 표시합니다. 관리자 데이터는 기존 MSW 핸들러에서만 제공하며, 화면은 공통 fetch 요청 함수를 사용합니다.
